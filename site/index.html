Right-size pods where they run.

K8s Tailor learns what each container really uses and resizes the running pod in place, through the Kubernetes pods/resize subresource. No restart, no recreated pod, and a reason recorded for every change.

What it does, and what you can check

Resizes in place
Running pods are resized, not recreated. The project's smoke test asserts that the pod UID and restartCount are unchanged after a resize. Controller rollouts and Knative Service patches exist as fallbacks, and an opt-in admission webhook applies the same plan when a pod is created.
Learns from OOM kills
When a container with a memory limit is OOMKilled, its limit is protected at limit × 1.5 for 30 days, so a later shrink cannot push it back to the value that killed it. The floor survives engine restarts.
Explains every change
Each recommendation shows its quantile, peak, forecast and headroom breach, plus the exact dry-run kubectl patch. Every applied change is a Kubernetes Event and, with ClickHouse, a durable record.
Knows about sidecars
Istio, Linkerd and Vault containers are classified and sized from their own usage. They stay recommend-only until you opt them in; init containers are never touched.
Gates you can read
Per-resource confidence, a shrink-only or grow-only direction, HPA hold, PodDisruptionBudget budget, QoS checks, cooldowns and one global pause switch. Limits are never shrunk in place.

Plain statistics, applied carefully

No model to trust. Three steps you can audit in the technical reference.

  1. Measure

    Kubelet resource metrics (CPU rate, memory working set) go into a single-node VictoriaMetrics, in 5-minute steps over a 7-day window.

    • confidence
    • direction
    • HPA
    • PDB
    • QoS
    • cooldown

  3. Recommend

    A decay-weighted percentile (p90 CPU, p95 memory), memory floored at the observed peak, change-point trimming and a seasonal forecast that must prove itself first.

    • pause
    • ignore

  5. Actuate

    Through pods/resize on running pods. Nothing happens to a workload until a TailorPolicy selects it with an actuating mode.

Try it without risking anything

It ships inert. Install it, watch the recommendations, and turn actuation on for one namespace when you are ready.

1. Install

helm install k8s-tailor \
  oci://ghcr.io/nicacioliveira/k8s-tailor/charts/k8s-tailor \
  --version 0.2.0 -n k8s-tailor --create-namespace

Public images for linux/amd64 and linux/arm64. Needs Kubernetes 1.33 or later.

2. Opt one namespace in

apiVersion: tailor.k8s-tailor.dev/v1alpha1
kind: TailorPolicy
metadata: { name: pilot }
spec:
  priority: 100
  selector: { namespaces: ["my-pilot-ns"] }
  mode: InPlace
  direction: Down   # never raises anything

Kill switch at any time: kubectl patch tailorconfig cluster --type=merge -p '{"spec":{"paused":true}}'

What it is not, and what has been checked

Deliberately not

  • A FinOps platform, a horizontal autoscaler, a node autoscaler or an ML system.
  • A source of real savings numbers: dollar figures are estimates from static prices unless you wire OpenCost.
  • Stable yet: the CRDs are v1alpha1 and the project is pre-1.0.

Details and reasons: known limitations.

Checked so far

  • Go tests under -race in CI, plus Helm, MCP and auth-gate jobs.
  • End-to-end runs on a single-node k3s (v1.34), including in-place resize with an unchanged pod UID, sidecars, webhook and leader election.
  • A backtest of nine synthetic scenarios against KRR-style and VPA-style baselines: a simulation, not production evidence.
  • Not checked: long-running use on a real production fleet.

Method and numbers: end-to-end results, backtest.
