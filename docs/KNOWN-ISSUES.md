# Known limitations and design decisions

What the engine deliberately does not do, and what it cannot know, each with the reason and what you can do about it. Everything else is documented in [TECHNICAL.md](TECHNICAL.md) and [CONFIGURATION.md](CONFIGURATION.md).

## Sizing

- **The OOM ceiling ignores LimitRange and node allocatable unless you opt in.** By default the learned memory floor is capped at `peak x OOM_MEM_CAP_FACTOR` (default 4) and the policy's `memory.max`, because reading nodes and LimitRanges needs extra RBAC. `tailor.rbac.clusterLookups=true` adds `list` on `nodes` and `limitranges` and caps every memory request at the largest Ready, uncordoned node's allocatable memory and the namespace LimitRange max (taints, affinities and a `Pod`-type LimitRange max are not evaluated). Without it, a request above the largest node leaves the pod `Pending`: set `memory.max` to the largest value you can schedule.
- **A node-level OOM and a cgroup OOM look the same.** Kubernetes reports `OOMKilled` in both cases, so a kill caused by node memory pressure also raises the floor. The floor expires after `OOM_FLOOR_TTL` (30 days). Use `memory.max` to bound it, or delete the floor annotation (`tailor.k8s-tailor.dev/oom-floor`) on the workload.
- **A CPU-greedy container is parked, not sized.** Usage pinned at the CPU limit makes the engine raise the limit by `CPU_LIMIT_GROWTH_FACTOR` per step; after `CPU_CENSOR_MAX_STEPS` (default 3) raises that the usage still pins at, the limit is parked at the last step and the container is marked `cpuGreedy` until usage falls below 80% of it. A container that wants unbounded CPU cannot be measured, so the parked limit is a bound, not a size. Set `cpu.max` when you know the ceiling. The run of raises is counted in memory: an engine restart counts it again from the live limit.
- **Envoy does not change concurrency after a resize.** Runtimes that size worker pools from the CPU limit at start-up keep their old pool until restarted. Restart the proxy (or the pod) after a large change.
- **Throttling in short bursts needs cAdvisor series.** Containers throttled inside 100 ms CFS periods while their 5-minute average stays low are only detected through `container_cpu_cfs_*` series. The bundled VictoriaMetrics scrapes them (job `kubelet-cadvisor`, two series only). With your own Prometheus, point `tailor.vmThrottleJob` (`VM_THROTTLE_JOB`) at your cAdvisor job; otherwise the signal is simply absent.
- **Change-point detection uses the most recent split.** On a real regime change it discards part of the old regime (up to about 25 percent of the window). A "best split" variant was implemented and measured on the backtest; it made three runs worse, so it was reverted ([BACKTEST.md](BACKTEST.md)). Regimes shorter than about 30 minutes per hour are never seen as a regime.
- **Bursty load sits above the request more often at the default quantile.** The CPU quantile defaults to 0.90. The burstiness index (`p99 / p90`) is exposed for every container; enable `autoQuantile: true` on a policy to raise the quantile to 0.95 automatically above the threshold, or use the `bursty` profile (`tailor.presets.enabled=true`, then `profileRef: bursty`) by hand. The automatic rule is off by default, and on the backtest it lowers the risk to about the KRR-style level at a cost close to KRR's, not below the default's.

## Resize and restart behaviour

- **Guaranteed pods are resized only with the opt-in, and their memory never shrinks.** By default a Guaranteed pod is left alone (`tailor_resize_skipped_total{reason="guaranteed_qos"}`; the webhook does not touch a Guaranteed template). `guaranteed: resizeBoth` resizes request and limit together so the pod stays Guaranteed: CPU grows and shrinks, memory only grows, because the kubelet applies a lowered memory limit best effort and `request == limit` near the peak turns a small error into an OOM. The upstream limitation stays: nodes using the static CPU or memory manager policy cannot resize in place, and pods with pod-level `spec.resources` keep the skip.
- **"Applied" reads the pod spec on kubelets older than 1.33.** From 1.33 the engine reads `status.containerStatuses[].resources`. Where the kubelet does not populate it, "Applied" and the waste figures fall back to `spec`, which shows the requested value, not the effective one, while a resize is Pending or Infeasible.
- **No desired replica count for `group` and bare Pods.** The disruptive rolling compares Ready replicas with `spec.replicas` (Deployment, StatefulSet; `desiredNumberScheduled` for DaemonSet; the sum over the revision Deployments for a Knative Service) read live before each restart. TailorGroups and bare Pods have no such number, so only the other guards apply (PDB, cooldown, no Pending replica).
- **Bare Pods keep no history across recreation.** Cooldown, failure backoff, rolling state and the OOM floor live in annotations on the pod, so a recreated bare Pod starts over. Controllers keep the cooldown on the template, and the OOM floor on the workload (Deployment, StatefulSet, DaemonSet, Knative Service) or on the TailorGroup.
- **History of replaced pods is attributed by generated name, and by memory for grouped units.** Series of pods that no longer exist are matched through `<ReplicaSet>-<suffix>` and `<DaemonSet>-<suffix>`; `ksvc` and `group` pods are remembered while the engine sees them alive and stay attributed for one `WINDOW`. Not covered: a ReplicaSet already garbage-collected (beyond `revisionHistoryLimit`), grouped pods that disappeared before this engine process saw them (the memory is not persisted, so an engine restart loses it), and bare Pods. The detail chart plots live pods only.

## Webhook

- **Decisions are recorded on observation, not at admission.** `/mutate` writes nothing to the decision log, so a forged AdmissionReview cannot fabricate decisions. The leader records the decision when it sees the pod (up to one `RECONCILE_EVERY`, 30 s, later), only if the pod's requests match the admission mark. It does not record while the engine is paused or without a leader, for pods in excluded namespaces, or for a pod resized in place before the first observation. On a leader failover a pod admitted just before the new term can be recorded twice.
- **Pods created right after an engine start rely on the warm cache.** The leader writes the webhook-servable recommendations to the ConfigMap `k8s-tailor-warm` and a starting replica loads them, so `reason="warming_up"` falls to about zero after a restart. It is still counted when there is no cache: the first install, one older than `WARM_TTL`, `tailor.warmCache.enabled=false`, a missing RBAC rule, or a cluster whose namespace has more webhook-servable containers than fit a ConfigMap. Loaded entries serve the webhook only. A call that never reaches a ready engine pod falls under `failurePolicy: Ignore`.

## Operations

- **Up to about 2 s of decisions are lost on SIGKILL.** The ClickHouse sink batches (500 rows or 2 s). A normal shutdown flushes; a kill after the grace period does not. The Kubernetes Event is still emitted.
- **The in-memory decision buffer is per replica.** Without ClickHouse, `/api/actuations` shows only what the answering replica saw. Use ClickHouse for a consistent history with `tailor.replicas > 1`.
- **GitOps tools revert a template the engine resized.** With `apply: Rollout`, `InPlacePreferred` falling back to a rollout, Knative Services or `proxyAnnotations`, the engine patches the controller template. Re-applying your manifest writes your values back, triggers a rollout, and the engine resizes again after its cooldown. Use `apply: InPlace`, stop declaring `resources` for managed containers in Git, or tell the tool to ignore those fields ([deploy/argocd/workload-application.yaml](../deploy/argocd/workload-application.yaml), [deploy/flux/](../deploy/flux/)).
- **`certMode: helm` and generated secrets are not stable under `helm template`.** Without `lookup`, every render generates a new CA and new passwords. The chart fails explicitly in that case; with GitOps use `certMode: certManager` or `existingSecret`, and set `clickhouse.auth.existingSecret` and `mcp.auth.existingSecret`.
- **Probes under NetworkPolicy depend on the CNI.** Kubelet probes originate on the node. Calico, Cilium and kube-router allow them; other CNIs may not. Check `kubectl describe pod` for probe failures after enabling `networkPolicy.enabled`.
- **vmsingle upgrades on provisioners that ignore `fsGroup`.** A volume written as root on a hostPath-type PV stays root-owned and the non-root vmsingle cannot write. The opt-in overlay `-f chart/values-vmsingle-chown.yaml` adds an init container that chowns the volume to 65534 (only `CAP_CHOWN`, read-only root filesystem); it is a values overlay, not a boolean, because the `victoria-metrics-single` subchart takes `server.initContainers` as a raw list and a value of this chart cannot template into a subchart's values. Its render is tested; it was not run on a provisioner that ignores `fsGroup` with root-owned data.
- **Backtest versus reconciler.** `reconciler.Decide` covers the in-place path of a Burstable pod without HPA, pending resize or PDB block. The disruptive rolling (`PlanInPlace`, `Cooled`, `RollingGate`) and the rollout path (`PlanRollout`) are replayed per replica on traces that declare a `Disruption` (the `restart-rolling` scenario); the other scenarios, and the per-pod guards outside those paths (QoS, failure backoff, HPA, the live PDB read), are not replayed ([BACKTEST.md](BACKTEST.md)).
